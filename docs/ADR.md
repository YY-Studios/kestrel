# Architecture Decision Records

## 철학

MVP 속도와 **안전**을 최우선으로 둔다. 자동매매는 잘못되면 돈이 나가므로, 모의투자(paper)를 기본값으로 깔고 실전은 의식적으로만 켠다. 백엔드 경험이 얕은 팀이므로, 한 번에 다 짊어지지 않고 작동하는 최소 구현부터 손으로 이해하며 넓혀간다. 외부 의존성과 운영 복잡도를 최소화한다.

---

### ADR-001: 매매 엔진을 FastAPI 밖 별도 워커 프로세스로 분리

**결정**: 상시 시세 감시·주문 로직을 FastAPI(api/) 안이 아니라 독립 Python 워커(engine/)로 둔다.
**이유**: 자동매매의 본질은 아무도 브라우저를 안 켜도 계속 도는 것이다. FastAPI는 요청-응답용이라 거기서 무한 루프를 돌리면 서버가 막힌다. 서버리스(Edge Function)도 짧게 실행되고 죽어서 못 한다.
**트레이드오프**: 띄워야 할 프로세스가 둘로 늘어 배포·운영이 약간 복잡해진다. 대신 책임이 명확히 분리되고, MVP 단계에선 단순 `while True + sleep` 루프로 충분하다 (Celery/APScheduler는 2차).

### ADR-002: 증권사는 한국투자(KIS) Open API REST 채택 `[Deprecated]`

> **Deprecated — ADR-007로 대체됨.** 미국 주식 단기 스윙으로 방향을 전환하면서 증권사를 Alpaca로 변경했다. 아래는 이력 보존용 원문이다.

**결정**: 키움이 아니라 한국투자(KIS) REST API를 쓴다.
**이유**: 키움 OpenAPI는 윈도우 OCX/COM 기반이라 서버·컨테이너 환경에서 붙이기가 지옥이다. KIS는 깔끔한 REST라 HTTP로 바로 붙고 Python 예제도 풍부하다. 백엔드 처음인 팀에 훨씬 친절하다.
**트레이드오프**: 키움 대비 일부 기능/속도 차이가 있을 수 있으나 MVP 범위에선 무관하다. 나중에 증권사를 바꾸려면 packages/kis-client를 교체해야 한다(그래서 클라를 공용 패키지로 격리 — ADR-003).

### ADR-003: KIS 클라이언트를 공용 패키지(packages/kis-client)로 분리 `[Deprecated]`

> **Deprecated — ADR-008로 대체됨.** 증권사 종속을 제거하기 위해 packages/broker-client 추상화 계층으로 발전시켰다. 아래는 이력 보존용 원문이다.

**결정**: KIS 연동 코드를 api/·engine/에 각각 두지 않고 packages/kis-client 하나로 만들어 둘이 공유한다.
**이유**: 같은 KIS 호출 코드가 두 벌로 갈라지면 "왜 KIS 클라가 두 개지" 혼란이 생기고, 토큰 발급·주문 로직이 어긋난다. 한 곳에서 관리한다.
**트레이드오프**: 워크스페이스 패키지 구성이 약간 필요하다(uv 워크스페이스로 해결). 대신 증권사 교체·수정 지점이 한 곳으로 모인다.

### ADR-004: 시세 저장에 시계열DB를 쓰지 않고 MVP는 Supabase PostgreSQL만

**결정**: 시세 틱 데이터를 위한 시계열DB(TimescaleDB 등) 도입을 MVP에서 보류하고, 모든 데이터를 Supabase PostgreSQL에 둔다.
**이유**: MVP는 단일 종목·단일 조건이라 저장할 시세량이 적다. 시계열DB는 다종목·고빈도로 갈 때 의미가 생긴다. 지금 도입하면 운영할 DB가 둘로 늘어 과하다.
**트레이드오프**: 나중에 시세를 대량 적재·집계하게 되면 PostgreSQL 성능 한계에 부딪혀 시계열DB로 이전이 필요할 수 있다. 그때 별도 ADR로 다룬다.

### ADR-005: 모의투자(paper) 모드를 기본값으로

**결정**: 증권사 클라이언트(broker-client)의 기본 동작을 모의투자(paper) 도메인으로 고정한다. 실전(real)은 환경변수로 명시적으로만 켠다.
**이유**: 개발·테스트 중 실수로 실주문이 나가면 실제 손실이 발생한다. 기본을 안전한 쪽에 둔다.
**트레이드오프**: 실전 전환 시 한 단계(환경변수/플래그)를 의식적으로 거쳐야 한다 — 의도된 마찰이다.

### ADR-006: 데이터·인증 레이어로 Supabase 채택

**결정**: 자체 백엔드 인증/CRUD를 짜는 대신 Supabase(PostgreSQL + Auth + Realtime)를 쓴다.
**이유**: 프론트가 강하고 백엔드가 처음인 팀이다. 인증·CRUD·실시간 구독 같은 "지루한 백엔드"를 Supabase가 대신해줘 핵심(매매 엔진)에 집중할 수 있다.
**트레이드오프**: Supabase 서비스에 묶인다. 상시 워커(engine)는 Supabase가 대신 못 하므로 별도로 둔다(ADR-001).

### ADR-007: 증권사를 Alpaca로 변경 (KIS 대체)

**결정**: 한국투자(KIS) 대신 Alpaca Open API(REST + WebSocket)를 쓴다. 대상 시장은 미국 주식, 기본은 Alpaca paper trading 계정이다. ADR-002를 대체한다.
**이유**: 프로젝트 방향을 미국 주식 단기 스윙(시나리오 1)으로 전환했다. Alpaca는 commission-free라 분할매수·잦은 진입/청산에 수수료 부담이 없고, REST로 주문·계좌 조회가 깔끔하며 WebSocket으로 실시간 시세를 받는다. paper trading 계정을 기본 제공해 안전 기본값(ADR-005)과도 맞는다.
**트레이드오프**: 한국 시장은 더 이상 지원하지 않는다. USD 환·미국 세제·시장 시간대(한국 야간) 같은 운영 고려가 생기나 MVP 범위 밖으로 둔다. Alpaca 장애 시 대안 증권사로 갈아탈 수 있게 ADR-008의 추상화로 격리한다.

### ADR-008: broker-client 추상화 계층 도입 (kis-client 대체)

**결정**: 증권사 연동을 packages/broker-client 하나로 두되, **증권사 추상 인터페이스와 구현체를 분리**한다. MVP 구현체는 Alpaca다. api·engine은 추상 인터페이스만 import 한다. ADR-003을 대체·발전시킨다.
**이유**: 증권사를 다시 바꿀 가능성(가격·기능·지역)을 미리 격리한다. 인터페이스를 고정하면 구현체(Alpaca → 타 증권사) 교체 시 api/engine 코드를 건드리지 않는다. 호출 코드가 두 벌로 갈라지는 것도 막는다(ADR-003의 원래 의도 유지).
**트레이드오프**: 추상화 계층만큼의 보일러플레이트가 생긴다. 대신 증권사 교체·수정 지점이 한 곳(구현체)으로 모이고, 테스트 시 가짜 구현(fake)으로 대체하기 쉬워진다.

### ADR-009: 시나리오 1 복합 전략 채택 (단일 조건 대체)

**결정**: "단일 종목·단일 조건"에서 **시나리오 1 복합 전략**(추세 추종 필터 → 눌림목 포착 → 반등 신호 2개 이상 → 3회 분할매수 → 익절/손절)으로 전환한다.
**이유**: 단일 조건(예: RSI 30)은 노이즈에 약하고, 추세를 거스르는 진입을 막지 못한다. 추세 필터로 진입 자격을 거르고 여러 지표의 합의로 반등을 확인하면 오진입이 줄고, 분할매수·익절/손절로 리스크를 관리할 수 있다.
**트레이드오프**: engine의 평가 로직과 상태 추적(분할매수 단계·평단가·목표가·손절가)이 복잡해진다. 따라서 조건 평가·주문 로직의 테스트 비중을 높여 TDD로 간다(CLAUDE.md 개발 프로세스). 지표 계산을 위해 일정 길이의 과거 시세(이동평균 60일 등)가 필요하다.
