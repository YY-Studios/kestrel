# Architecture Decision Records

## 철학

MVP 속도와 **안전**을 최우선으로 둔다. 자동매매는 잘못되면 돈이 나가므로, 모의투자(paper)를 기본값으로 깔고 실전은 의식적으로만 켠다. 백엔드 경험이 얕은 팀이므로, 한 번에 다 짊어지지 않고 작동하는 최소 구현부터 손으로 이해하며 넓혀간다. 외부 의존성과 운영 복잡도를 최소화한다.

---

### ADR-001: 매매 엔진을 FastAPI 밖 별도 워커 프로세스로 분리

**결정**: 상시 시세 감시·주문 로직을 FastAPI(api/) 안이 아니라 독립 Python 워커(engine/)로 둔다.
**이유**: 자동매매의 본질은 아무도 브라우저를 안 켜도 계속 도는 것이다. FastAPI는 요청-응답용이라 거기서 무한 루프를 돌리면 서버가 막힌다. 서버리스(Edge Function)도 짧게 실행되고 죽어서 못 한다.
**트레이드오프**: 띄워야 할 프로세스가 둘로 늘어 배포·운영이 약간 복잡해진다. 대신 책임이 명확히 분리되고, MVP 단계에선 단순 `while True + sleep` 루프로 충분하다 (Celery/APScheduler는 2차).

### ADR-002: 증권사는 한국투자(KIS) Open API REST 채택 `[Accepted]`

> **재확정(Accepted) — Alpaca 전환(ADR-007)을 되돌려 KIS로 회귀했다.** 단, 거래 대상은 미국 주식 그대로다(KIS 해외주식 API 사용 — ADR-010). 아래 원문의 "깔끔한 REST·풍부한 Python 예제"라는 채택 근거는 유효하며, 구현 패키징은 현재 broker-client 추상화(ADR-008)를 따른다.

**결정**: 키움이 아니라 한국투자(KIS) REST API를 쓴다.
**이유**: 키움 OpenAPI는 윈도우 OCX/COM 기반이라 서버·컨테이너 환경에서 붙이기가 지옥이다. KIS는 깔끔한 REST라 HTTP로 바로 붙고 Python 예제도 풍부하다. 백엔드 처음인 팀에 훨씬 친절하다.
**트레이드오프**: 키움 대비 일부 기능/속도 차이가 있을 수 있으나 MVP 범위에선 무관하다. 나중에 증권사를 바꾸려면 broker-client 구현체를 교체하면 된다(그래서 연동을 공용 패키지로 격리 — ADR-008).

### ADR-003: KIS 클라이언트를 공용 패키지(packages/kis-client)로 분리 `[Deprecated]`

> **Deprecated — ADR-008로 대체됨.** 증권사 종속을 제거하기 위해 packages/broker-client 추상화 계층으로 발전시켰다. 아래는 이력 보존용 원문이다.

**결정**: KIS 연동 코드를 api/·engine/에 각각 두지 않고 packages/kis-client 하나로 만들어 둘이 공유한다.
**이유**: 같은 KIS 호출 코드가 두 벌로 갈라지면 "왜 KIS 클라가 두 개지" 혼란이 생기고, 토큰 발급·주문 로직이 어긋난다. 한 곳에서 관리한다.
**트레이드오프**: 워크스페이스 패키지 구성이 약간 필요하다(uv 워크스페이스로 해결). 대신 증권사 교체·수정 지점이 한 곳으로 모인다.

### ADR-004: 시세 저장에 시계열DB를 쓰지 않고 MVP는 Supabase PostgreSQL만

**결정**: 시세 틱 데이터를 위한 시계열DB(TimescaleDB 등) 도입을 MVP에서 보류하고, 모든 데이터를 Supabase PostgreSQL에 둔다.
**이유**: MVP는 단일 종목·단일 조건이라 저장할 시세량이 적다. 시계열DB는 다종목·고빈도로 갈 때 의미가 생긴다. 지금 도입하면 운영할 DB가 둘로 늘어 과하다.
**트레이드오프**: 나중에 시세를 대량 적재·집계하게 되면 PostgreSQL 성능 한계에 부딪혀 시계열DB로 이전이 필요할 수 있다. 그때 별도 ADR로 다룬다.

### ADR-005: 모의투자(paper) 모드를 기본값으로

**결정**: 증권사 클라이언트(broker-client)의 기본 동작을 모의투자(paper) 도메인으로 고정한다. 실전(real)은 환경변수로 명시적으로만 켠다.
**이유**: 개발·테스트 중 실수로 실주문이 나가면 실제 손실이 발생한다. 기본을 안전한 쪽에 둔다.
**트레이드오프**: 실전 전환 시 한 단계(환경변수/플래그)를 의식적으로 거쳐야 한다 — 의도된 마찰이다.

### ADR-006: 데이터·인증 레이어로 Supabase 채택

**결정**: 자체 백엔드 인증/CRUD를 짜는 대신 Supabase(PostgreSQL + Auth + Realtime)를 쓴다.
**이유**: 프론트가 강하고 백엔드가 처음인 팀이다. 인증·CRUD·실시간 구독 같은 "지루한 백엔드"를 Supabase가 대신해줘 핵심(매매 엔진)에 집중할 수 있다.
**트레이드오프**: Supabase 서비스에 묶인다. 상시 워커(engine)는 Supabase가 대신 못 하므로 별도로 둔다(ADR-001).

### ADR-007: 증권사를 Alpaca로 변경 (KIS 대체) `[Deprecated]`

> **Deprecated — ADR-010으로 되돌림.** Alpaca로 갔다가 KIS로 회귀했다(거래 대상 미국 주식은 유지). 사유: 한국 거주자가 Alpaca로 **실전** 운용 시 해외 송금·입출금 수수료와 환전 마찰이 크고, 비용 최소화가 우선이라 KIS 해외주식으로 돌아간다. 아래는 이력 보존용 원문이다.

**결정**: 한국투자(KIS) 대신 Alpaca Open API(REST + WebSocket)를 쓴다. 대상 시장은 미국 주식, 기본은 Alpaca paper trading 계정이다. ADR-002를 대체한다.
**이유**: 프로젝트 방향을 미국 주식 단기 스윙(시나리오 1)으로 전환했다. Alpaca는 commission-free라 분할매수·잦은 진입/청산에 수수료 부담이 없고, REST로 주문·계좌 조회가 깔끔하며 WebSocket으로 실시간 시세를 받는다. paper trading 계정을 기본 제공해 안전 기본값(ADR-005)과도 맞는다.
**트레이드오프**: 한국 시장은 더 이상 지원하지 않는다. USD 환·미국 세제·시장 시간대(한국 야간) 같은 운영 고려가 생기나 MVP 범위 밖으로 둔다. Alpaca 장애 시 대안 증권사로 갈아탈 수 있게 ADR-008의 추상화로 격리한다.

### ADR-008: broker-client 추상화 계층 도입 (kis-client 대체)

**결정**: 증권사 연동을 packages/broker-client 하나로 두되, **증권사 추상 인터페이스와 구현체를 분리**한다. MVP 구현체는 KIS(해외주식)다. api·engine은 추상 인터페이스만 import 한다. ADR-003을 대체·발전시킨다.
**이유**: 증권사를 다시 바꿀 가능성(가격·기능·지역)을 미리 격리한다. 인터페이스를 고정하면 구현체(KIS ↔ 타 증권사) 교체 시 api/engine 코드를 건드리지 않는다. 실제로 이번에 Alpaca→KIS로 구현체만 바꾸는 회귀에서 이 추상화가 값을 했다. 호출 코드가 두 벌로 갈라지는 것도 막는다(ADR-003의 원래 의도 유지).
**트레이드오프**: 추상화 계층만큼의 보일러플레이트가 생긴다. 대신 증권사 교체·수정 지점이 한 곳(구현체)으로 모이고, 테스트 시 가짜 구현(fake)으로 대체하기 쉬워진다.

### ADR-009: 시나리오 1 복합 전략 채택 (단일 조건 대체)

**결정**: "단일 종목·단일 조건"에서 **시나리오 1 복합 전략**(추세 추종 필터 → 눌림목 포착 → 반등 신호 2개 이상 → 3회 분할매수 → 익절/손절)으로 전환한다.
**이유**: 단일 조건(예: RSI 30)은 노이즈에 약하고, 추세를 거스르는 진입을 막지 못한다. 추세 필터로 진입 자격을 거르고 여러 지표의 합의로 반등을 확인하면 오진입이 줄고, 분할매수·익절/손절로 리스크를 관리할 수 있다.
**트레이드오프**: engine의 평가 로직과 상태 추적(분할매수 단계·평단가·목표가·손절가)이 복잡해진다. 따라서 조건 평가·주문 로직의 테스트 비중을 높여 TDD로 간다(CLAUDE.md 개발 프로세스). 지표 계산을 위해 일정 길이의 과거 시세(이동평균 60일 등)가 필요하다.
**임계값은 범위가 아니라 단일 설정값(config)으로 고정한다**: 익절/손절/눌림목 %, RSI·볼린저·MACD 주기, 고점 lookback 길이 등은 문서에 범위(예: +7~10%)로 적혀 있으나, 구현에서는 **하나의 확정값을 config로 고정**하고 그 값으로 테스트한다. 범위를 코드 분기로 만들지 않는다(테스트 가능성·재현성 확보). 값 변경은 config 수정 + 재테스트로 한다.

### ADR-010: KIS 해외주식 API로 미국 주식을 거래 (Alpaca 회귀)

**맥락**: 미국 주식은 전략적으로 유리하다 — 유동성이 풍부하고, 증권거래세가 없어 분할매수·잦은 청산에 마찰이 적으며, 추세가 깨끗하다. 그래서 거래 대상은 미국 주식으로 유지한다. 그러나 한국 거주자가 미국 증권사(Alpaca)로 **실전** 운용을 하려면 해외 송금·입출금 수수료와 원↔달러 환전 마찰이 커서 비용·운영 부담이 크다. ADR-007(Alpaca)을 되돌린다.
**결정**: 증권사는 **한국투자(KIS)**, 거래 대상은 **미국 주식**으로 한다. KIS 해외주식 Open API(REST + WebSocket)를 쓰고, 모의투자는 KIS **해외주식 모의(해외 리그)** 계좌를 기본값(paper)으로 둔다. broker-client의 MVP 구현체를 Alpaca → KIS로 교체한다(인터페이스는 ADR-008 유지).
**이유**: 국내 증권사 계좌 하나로 입출금·환전이 끝나 실전 전환 시 마찰과 비용이 작다. 미국 주식의 전략적 이점은 그대로 가져간다. 구현은 커뮤니티 라이브러리 [python-kis](https://github.com/Soju06/python-kis)(국내/해외 통합 인터페이스, 자동 재연결/토큰 관리 지원) 검토로 KIS 해외주식 API의 빈약함을 보완할 수 있다(실제 도입은 코드 단계 결정).
**해외 모의투자 지원 확인**: KIS 해외주식 **모의투자 지원이 확인됐다.** 근거 — 모의투자 전용 도메인 `openapivts.koreainvestment.com:29443`이 존재하고, 미국 주식 모의 주문 TR ID(매수 `VTTT1002U` / 매도 `VTTT1001U`)가 제공된다. 따라서 paper(해외 리그) 기본값 전제는 유효하다.

**모의투자 제약 (반드시 반영)**:
1. **모의투자는 일부 해외 종목만 매매 가능하다.** 워치리스트는 "모의 거래 가능 종목" 범위 안에서 선정해야 한다. 구체 종목 목록은 **모의투자 신청 후 확인**해야 하며, 현재는 **미확정**이다(특정 종목으로 워치리스트를 못 박지 않는다).
2. **모의투자 미국 주문은 지정가(`00`)만 가능하고 시장가는 불가능하다.** 진입·청산 모두 지정가로 주문하되, 현지 거부를 막기 위해 현재가 대비 ±10% 이내 버퍼 가격을 쓴다(PRD 주문 방식 참고). real 전환 시 시장가 사용 여부는 별도 결정.

**트레이드오프**:
- **운영 시간대**: 미국 정규장이 한국 새벽(대략 23:30~06:00, 미국 서머타임 적용 시 22:30~05:00)이라 engine이 새벽에 가동돼야 한다. **서머타임(DST) 전환 처리**가 필요하다(고정 오프셋 금지, 미국 동부 시간 기준으로 계산).
- KIS 해외주식 API는 Alpaca보다 문서·기능이 빈약하고 호가/체결 데이터·레이트리밋 제약이 있을 수 있다. python-kis로 보완하되, 안 되는 부분은 broker-client 인터페이스 뒤에서 흡수한다.
- commission-free였던 Alpaca와 달리 KIS 해외주식은 매매 수수료가 있다(전략의 손익 계산에 반영 필요 — 코드 단계).

### ADR-011: 전략은 1개(시나리오 1)지만 내부 구조는 확장 가능하게

**결정**: 1차 MVP는 전략을 **시나리오 1 하나만** 둔다. 사용자는 전략을 고르는 게 아니라 그 전략의 **ON/OFF와 임계값 조절**만 한다. 단 내부 데이터 구조는 **"전략 = 이름 + 임계값 묶음"** 단위로 분리해, 나중에 전략을 추가할 때 구조를 갈아엎지 않게 설계한다(broker-client 추상화(ADR-008)와 같은 취지 — 지금은 구현체가 하나여도 경계를 미리 긋는다).
**이유**: 전략이 시나리오 1 하나뿐인데 "여러 전략 중 선택" UI를 만들면 선택지가 없는 빈 화면이 된다. 동시 다중 전략은 자금 배분·종목 충돌(같은 종목을 두 전략이 동시에)·검증 복잡도가 커져 MVP에 과하다. 그래도 전략을 코드에 하드코딩으로 박아버리면 두 번째 전략을 넣을 때 전부 뜯어야 하므로, 데이터 경계만 미리 만든다.
**트레이드오프**: 단일 전략인데 "전략 묶음" 구조를 두는 건 약간의 선투자다. 대신 향후 전략 추가(예: 트레일링 청산 변형, 시나리오 2)나 [청산 고도화](ROADMAP.md) 도입 시 임계값 세트만 추가하면 되어 비용이 작다. 임계값 자체는 ADR-009대로 단일 config 값으로 고정·테스트한다.
